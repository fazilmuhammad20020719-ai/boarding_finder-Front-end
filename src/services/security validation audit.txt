# Security & Input Validation Audit Report

This document reviews the current state of user input validation across the BoardingFinder system (Frontend & Backend) and outlines the strict validation rules required to make the platform secure against XSS, SQLi, malicious uploads, and data corruption.

---

## 1. User Registration & Profile
*Current State:* The frontend only checks if fields are empty (`if (!name)`). The backend (`registerStudent.js`, `registerOwner.js`) only checks for null values. No length restrictions, format validation, or password complexity rules exist.

**Recommended Validation Rules (Frontend & Backend):**
- `name`: Required | Type: String | Length: Min 2, Max 50 | Allowed: `^[a-zA-Z\s\-']+$` (Letters, spaces, hyphens). *Sanitize leading/trailing spaces.*
- `email`: Required | Type: String | Length: Max 100 | Format: Strict Email Regex or `validator.isEmail()`. *Must be converted to lowercase.*
- `phone`: Required | Type: String | Length: 9 to 15 chars | Format: `^\+?[0-9\s\-]+$` (Allow international codes).
- `password`: Required | Type: String | Length: Min 8, Max 128 | Complexity: Must contain at least 1 uppercase, 1 lowercase, 1 number, and 1 special character.
- `role`: Required | Type: String | Allowed Enum: `['student', 'owner', 'admin']`. *Backend must strictly reject any other value.*

## 2. Login & Authentication
*Current State:* Basic null checks. Backend safely hashes using `bcrypt` and parameterized queries, preventing SQLi.
*Missing Security measures:*
- **Rate Limiting**: Backend MUST implement rate limiting (e.g., `express-rate-limit`: max 5 failed attempts per 15 mins) to prevent brute-force and credential stuffing attacks.

## 3. Listing Creation & Editing (Owner Forms)
*Current State:* Frontend does basic `.trim()` checks. Backend (`createListing.js`) does basic null checks. No bounds checking for numeric fields.

**Recommended Validation Rules (Frontend & Backend):**
- `title` / `propertyName`: Required | Type: String | Length: Min 5, Max 100. *Must escape HTML to prevent XSS.*
- `description`: Required | Type: String | Length: Min 20, Max 2000. *Must be sanitized on the backend using `DOMPurify` to prevent stored XSS attacks if rendered as HTML.*
- `price` / `security_deposit`: Required | Type: Numeric/Decimal | Bounds: Min 0 (No negative rents). Max 10,000,000. *Reject NaN or infinite values.*
- `latitude` / `longitude`: Optional/Required | Type: Decimal | Bounds: Lat between -90 and 90, Lng between -180 and 180.
- `amenities` / `rules`: Type: JSON/Object. *Backend must validate that keys are booleans and strip unknown keys to prevent Prototype Pollution.*

## 4. Booking & Contact Forms (Student Forms)
*Current State:* `createBooking.js` parses integers (`parseInt`) but lacks logical validation (e.g., duplicate bookings, past dates).

**Recommended Validation Rules (Frontend & Backend):**
- `move_in_date`: Required | Type: Date | Format: ISO 8601 (`YYYY-MM-DD`). *Backend MUST verify the date is in the future.*
- `duration_months`: Required | Type: Integer | Bounds: Min 1, Max 48.
- `message`: Optional | Type: String | Length: Max 500. *HTML must be strictly escaped.*

## 5. Search & Filter Inputs
*Current State:* Unvalidated query parameters are passed to the database.
*Missing Security measures:*
- `keyword` / `q`: Must be stripped of SQL wildcard characters (`%`, `_`) before being dynamically inserted into `ILIKE` searches to prevent slow-query DoS attacks.
- `minPrice` / `maxPrice`: Must be strictly cast to Numbers and validated (Min >= 0, MaxPrice > MinPrice).

## 6. File & Image Uploads (Critical Vulnerability)
*Current State:* Frontend uses `accept="image/*"`. Backend relies on basic Multer configuration.
*Missing Security measures:*
- **Malicious File Execution (RCE)**: Backend MUST validate the "Magic Bytes" (file signature) of uploads, not just the file extension or MIME type sent by the client.
- **Allowed Types**: Images must be strictly restricted to `image/jpeg`, `image/png`, and `image/webp`. Reject SVG (which can contain embedded XSS). Documents restricted to `application/pdf` or images.
- **Size Limits**: Max 5MB per image. Max 10MB per document.
- **Sanitization**: Uploaded filenames must be completely regenerated (e.g., using UUIDs) before saving. Never trust the user's `filename` to prevent Directory Traversal attacks (e.g., `../../etc/passwd`).

## 7. Global System Defenses
- **SQL Injection (SQLi)**: Currently, the backend uses `query(sql, [values])` which leverages parameterized queries. This is correctly implemented and safe.
- **Cross-Site Scripting (XSS)**: React safely escapes variables in the DOM by default. However, any backend data used in `dangerouslySetInnerHTML` must be sanitized.
- **Cross-Site Request Forgery (CSRF)**: Missing. Need to implement CSRF tokens for all state-mutating requests (POST, PUT, DELETE).
